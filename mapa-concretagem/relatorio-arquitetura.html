Mapa de Concretagem — Relatório técnico

Documento gerado a partir do código do repositório pwa-hub. Foco: PWA mapa-concretagem (fluxos, funções, persistência local e sincronização com Google Sheets via Apps Script).

1) Estrutura do app

Front-end

  • mapa-concretagem/index.html: layout das telas e modais (inclui o modal concretoTipoModal).
  • mapa-concretagem/styles.css: estilos.
  • mapa-concretagem/app.js: lógica do app (telas, eventos, persistência e APIs).

Conectividade com Google Sheets (Apps Script Web App)

O app usa duas URLs (dois Web Apps diferentes), definidas em mapa-concretagem/app.js: 
CONFIG.API_URL           // API "principal" (produção/liberação, inspeção, relatórios, etc.)
CONFIG.MONTAGEM_API_URL  // API de "montagem/usuários" (login, usuários, montagem de postes)
O padrão de chamada é POST com action e payload (JSON stringificado) usando URLSearchParams.

2) Persistência local (onde e como os dados são salvos no navegador)

Chaves usadas no LocalStorage

  • pwa_liberacao_inspecao_v1 (STORAGE_KEY): DB principal com { records: [], events: [] }.
  • pwa_liberacao_submit_locks_v1 (SUBMIT_LOCKS_KEY): trava contra reenvio/duplicidade (inspeção/liberação).
  • pwa_formas_clicadas_hoje (CLICKED_FORMS_KEY): marca formas clicadas no dia por setor (reseta ao trocar o dia).
  • pwa_montagem_postes_v1 (MONTAGEM_POSTES_KEY): DB local de montagem de postes (mapa postes[key]).
  • pwa_mapa_auth_session_v1 (AUTH_SESSION_KEY): sessão do usuário logado (nome + role).
  • pwa_acmp_notas_v1 (ACMP_NOTES_KEY): notas do acompanhamento de concretagem.
  • sidebarCollapsed: preferência visual.

DB principal (forma do JSON)

{
  "records": [ /* registros por forma/data/setor, incluindo liberação, tipo de concreto e inspeções */ ],
  "events":  [ /* eventos agregados para histórico/dashboards */ ]
}

3) Persistência online (Google Sheets) — como o app envia

Formato padrão das requisições

POST {CONFIG.API_URL ou CONFIG.MONTAGEM_API_URL}
Content-Type: application/x-www-form-urlencoded

action=<nome-da-acao>
payload=<json-stringificado>
Quando a API não está configurada (https://script.google.com/...) ou falha, o app retorna { skipped: true } e segue salvando localmente.

4) Telas (modos) e funções principais

Modos (telas)

  • HUB (menu inicial)
  • DASHBOARD (gráficos a partir do DB local)
  • LIBERACAO (Produção / Liberação: seleção de forma + tipo de concreto)
  • INSPECAO (Montagem / Inspeção: salvar inspeções em lote)
  • MONTAGEM_POSTES e MONTAGEM_POSTES_DETALHE (checklist + status)
  • RELATORIO (relatório por setor)
  • HISTORICO (histórico por data/tipo/forma)
  • ACOMPANHAMENTO (kpis/contagem)
  • ACMP_CONCRETAGEM (acompanhamento concretagem + notas)
  • USUARIOS (gerenciamento de usuários — visível conforme perfil)

5) Inventário de ações (API) chamadas pelo front-end

API principal (CONFIG.API_URL)

  • GET ?action=status: checagem de saúde/conexão (usado no status “Conectado com planilha”).
  • POST action=salvar_forma_click: registra liberação por forma (inclui tipo_concreto).
  • POST action=salvar_inspecao_lote: salva inspeções em lote ({ entries: [...] }).
  • GET ?action=inspecao_pendentes: lista itens pendentes para inspeção (opcionalmente filtra por setor).
  • GET ?action=relatorio_setor: relatório por setor/data.

API de montagem/usuários (CONFIG.MONTAGEM_API_URL)

  • POST action=autenticar_usuario: login.
  • POST action=listar_usuarios: lista usuários ativos.
  • POST action=criar_usuario: cria usuário.
  • POST action=excluir_usuario: desativa usuário (soft delete).
  • POST action=salvar_montagem_poste: grava/atualiza montagem de poste (upsert por key).
  • GET ?action=status (no Apps Script): status do backend.

6) Fluxos de dados (o que salva, onde salva, como salva)

6.1 Produção / Liberação: clique na forma + popup “Tipo de Concreto”

  • UI: ao clicar uma forma abre um modal popup com as opções Padrão, Vibrado, Concreto com Variação.
  • Local:
    • Marca “clicada hoje” em pwa_formas_clicadas_hoje (por setor + forma).
    • Atualiza/insere registro em pwa_liberacao_inspecao_v1 (record com concretoTipo e liberacao.status="1").
  • Sheets: envia POST action=salvar_forma_click para CONFIG.API_URL com payload incluindo tipo_concreto.

6.2 Inspeção: salvar em lote

  • Local: grava as inspeções no DB local (records[].inspecoes[]) e adiciona eventos em events[].
  • Sheets: tenta sincronizar via POST action=salvar_inspecao_lote em CONFIG.API_URL com { entries: [...] }.
  • Fallback: se a API não estiver configurada ou falhar, mantém como “salvo localmente”.

6.3 Montagem Postes: checklist + status

  • Local: DB pwa_montagem_postes_v1 guarda entradas por key.
  • Sheets: sincroniza via POST action=salvar_montagem_poste em CONFIG.MONTAGEM_API_URL.

6.4 Dashboards/Relatórios/Histórico

  • Local: dashboards usam db.events e db.records para KPIs e gráficos.
  • Sheets: quando disponível, o app consulta via GET (relatorio_setor, inspecao_pendentes).

7) Backends (Apps Script) presentes no repositório e onde gravam

Apps Script de montagem/usuários (no repo)

Arquivo: mapa-concretagem/AppsScript_montagem_poste.gs
  • usuarios_mapa: credenciais (nome/perfil/senha/ativo).
  • montagem_poste: montagem de postes (upsert por key).

Apps Script “unificado” (no repo) e compatibilidade

Arquivo: AppsScript_unificado.gs (referência no repo).
  • Ele implementa POST action=salvar_forma_click e grava na aba tecnica.
  • Ele não implementa (no arquivo atual do repo): status, relatorio_setor, inspecao_pendentes, salvar_inspecao_lote.
Se o Web App real apontado por CONFIG.API_URL já responde essas ações, então ele é um Apps Script diferente/mais completo do que o arquivo AppsScript_unificado.gs versionado aqui.

8) Observações importantes

  • O app foi desenhado para funcionar offline: sempre salva localmente e tenta sincronizar quando possível.
  • A “fonte de verdade” para dashboards e histórico é o DB local (records/events), com sincronização opcional.
  • Para inspeção/relatórios online funcionarem, o Apps Script do CONFIG.API_URL precisa suportar as ações que o front chama.
